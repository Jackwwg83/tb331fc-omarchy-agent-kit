0. 决策摘要

建议启动项目，但把明天的目标定为“查清本机通路并形成可审查实验方案”，而不是“必须刷成 Omarchy”。

目前有足够线索开展官方解锁核实、固件离线分析、采集工具开发及 ARM64 用户空间验证；但没有足够证据，批准对这台 ZUX OS 1.1.10.680 的 TB331FC 执行解锁、降级、刷写或 EDL 操作。

这不是认定原生移植做不到。结论是：尚缺本机证据、匹配恢复材料和可复现启动路径，不能把研究假设升级为硬件操作许可。

最合理的总体路线是：

                       ┌─ 官方申请条件 / 精确固件 / 解锁验证逻辑调查 ─┐
本机只读识别与备份准备 ─┤                                             ├─ 人工阶段决策
                       └─ Mac 上 ARM64 Omarchy 用户空间验证 ─────────┘
                                                                      │
                                            解锁与恢复证据过关后才进入 │
                                                                      ▼
         最小启动证据 → 显示/输入/电源/网络 → GPU + Wayland → Omarchy

两条并行路线各自出报告。Mac 虚拟机能跑 Omarchy，不等于平板能启动 Linux；平板解锁，不等于 Linux 驱动齐全。

1.2 需要修正的三项认识

第一，Omarchy 的 ARM64 路线已经比“只有民间实验”更进一步。 官方于 2026-09-18 宣布 Omarchy Dragon，公开工作重点是 Snapdragon X / X2 系列电脑，仍按具体机器推进。它提供有价值的 ARM 软件与安装器成果，但没有在该公告中承诺 TB331FC 支持。[S13]

第二，TB331FC 的解锁证据是混合的。 官方入口可访问；同型号存在历史失败报告，lenovoubl 上也有较新的失败记录。这些材料不构成“必然能解锁”，也不构成“绝对无法解锁”。本项目必须区分型号、完整固件、出厂分支和实际命令结果。[S01][S02][S03]

第三，邻近机型的 Linux 移植不能直接当成本机驱动表。 本次访问相关 postmarketOS 页面遇到访问限制，未重新核实之前提到的 TB128FU 功能表。不得将那份表写成已确认事实，更不得刷入其镜像。[S19]

2. 解锁研究：真正值得投入的方向

2.1 首选官方渠道，而不是先“试各种破解包”

联想/ZUI 官方解锁页仍存在，需要登录。页面区分普通序列号与 Bootloader_SN，并明确存在部分设备或版本不支持的情况；页面中还包含某些版本须经指定服务流程升级的条件提示。公开页面可读，不代表已经确认你的账号、型号和版本可以获批。[S01]

因此，第一个高价值实验不是刷入任何文件，而是由你手动完成：确认官网是否识别这台设备，取得明确的允许/拒绝/需服务站处理的结果。只把脱敏后的结果交给 Agent。账号、序列号、邮箱及设备专属文件留在你控制的本地目录。

若官网要求指定服务流程，记录原文、适用型号、版本要求及厂商工单。不要自行将“指定版本”理解为某个论坛旧版，更不要让 Agent 代替你接受服务或付费。

2.2 两条同型号失败记录说明了什么

2024-05-27 的联想社区发帖者称，TB331FC 使用官方申请到的 sn.img 时，写入步骤被锁定状态拒绝。它是第一人称失败记录，不是厂商根因分析。[S02]

lenovoubl 的 Issue #1（2026-03-12）报告：TB331FC / ZUI 15.1.328，生成文件能完成写入，但后续 OEM 解锁失败。它的系统分支和版本与你照片中的版本并不相同。[S03]

工程推论：必须把至少四个状态分开记录：申请文件成功、文件格式解析通过、写入步骤成功、锁状态真正改变。 不得用前三者替代第四者。也不能把某个错误归因于“缺少一个命令”，然后顺手执行更危险的 critical unlock、擦除或降级。

2.3 对 lenovoubl 的静态检查结论

本次读取了其公开仓库、前端页面和 js/main.js，没有在设备上运行它，也没有取得固定提交的完整离线副本。[S04][S05][S06]

在读取的主脚本中，生成过程是将固定头部/内容、序列号、填充与固定签名数据拼接；没有看到针对新序列号重新签名或向官方后端申请签名的流程。这说明它是需要核实适用条件的格式构造工具，不能仅凭代码能生成文件就认定能绕过本机验证。 是否存在特定引导程序行为、签名覆盖范围或历史兼容条件，需要再审查实际验证端；单看生成端不能定论。[S06]

前端提示还要求按初始操作系统选择分支。不要看到现在写着 ZUX，就自动选择 ZUX 分支；这是明天要验证的独立问题。[S05]

建议让 Claude 分析“验证端究竟检查什么”，Codex 做“输入/输出与结构解释是否可复现”的独立检查。禁止把真实设备标识直接提交给未经审查的第三方在线生成器。

2.4 四个可检验假设

假设 如何取证 通过标准 不能代替证据的东西
H1：本机官方流程可用 官网人工申请/咨询；完整版本与设备身份匹配 官方对本机明确答复，并有匹配方法、风险和恢复条件 官网有一个输入框
H2：文件分支或标识选错 比较官方说明、出厂资料、脱敏属性；本地比较文件结构 明确每个输入来自哪里，并能解释格式与验证逻辑 “长度是 64，所以一定选某分支”
H3：当前引导程序的策略不同 从可信匹配固件离线分析相关启动组件；关联版本与命令处理路径 能定位拒绝条件，区分格式、状态、签名、授权/策略错误 不同版本的成功截图

2.5 首日逆向工作的合理深度

先定位固件包里的启动组件、文件格式、版本、签名元数据及命令字符串；再为相关处理函数建立“输入 → 前置状态 → 验证 → 返回码”的说明。区分在二进制中看到字符串与证明该代码路径在这台设备上生效。

不要默认固件中的 abl、xbl 或分区名称一定如此；根据实际清单确定。工具也不是可信根：下载反汇编器、解析器及依赖须先审阅来源，外部代码只在无平板连接的隔离环境执行。首日不要求完成安全启动完整逆向，不以“必须攻破”为验收目标。

3. 恢复能力必须先于写入

3.1 必须区分三个“备份”

用户数据备份保存照片、文档、应用可导出数据和必要的账户恢复手段。原厂恢复包提供重装系统的材料。设备专属分区/校准数据可能关系到具体硬件的正常工作。三者不能互相替代。

库存 Android 上能运行 ADB，不表示可以读取所有块设备、获得解密后的所有应用数据，或制作完整可恢复镜像。本工具只采集信息，绝不宣称完成了固件或用户数据备份。

在无法读取某个敏感/专属分区时，记录为未知，不用提权或 EDL 来“补齐表格”。若拟议方案会触及这些未知区域，门槛不能通过。

3.2 恢复矩阵

使用 templates/recovery-matrix.md。至少回答：

故障层级 必须证明或明确记录的事
Android 正常 用户数据已备份；重要文件抽样可恢复；当前版本与身份可复核
Android 不启动，但 bootloader/recovery 可达 匹配固件来源、完整性、适用锁状态、恢复步骤及执行平台
只能低级下载模式连接 是否有本机匹配 loader/授权、执行工具与主机兼容性；没有证据就标未知
USB 完全不枚举/不能进模式 是否有厂商服务路径；这是残余风险，不要假装有软件保证

“没有经历过真砖恢复”与“毫无恢复准备”不是一回事。不要求故意刷坏来证明恢复能力，但必须具体到材料、工具、适用状态和仍未验证的部分。你要明确接受剩余风险，不能由 Agent 替你接受。

3.3 Mac 与救砖工具的边界

Google 提供 macOS 的 ADB/Fastboot，适合本机调查与后续经审批的正常启动链操作。[S20]

本次确认了 Lenovo Software Fix / Rescue and Smart Assistant 的官方入口，但抓取未提供可核对的本机兼容清单。因此，尚未确认它支持中国版 TB331FC、你的版本，或可在你的 Mac 上完成恢复。 不把“软件存在”写成“救砖可用”。[S11]

若后续方法依赖另一操作系统或驱动，先核对官方要求和本机型号支持。不要假定 Apple Silicon 上的 Windows 虚拟机等价于已经验证的恢复电脑；也不要在缺少具体需求前先购买硬件。

3.4 EDL 不等于万能后门

上游 EDL 工具文档涉及 loader、硬件标识、签名相关标识及厂商限制；本次没有找到并确认适用于这台设备的完整 loader/授权/恢复链。[S12]

项目规则：EDL 模式切换、上传 loader、执行 Firehose 命令，都不属于首日只读采集。 即使命令目的写着“读取 GPT”，之前上传的程序已获得不同级别的执行能力，不能因为最终是“读”就降低审批。

如果平板意外只显示低级下载设备：停止，记录主机枚举信息与最后一次人工操作；不得自动扫描并尝试一组 loader，不得自动擦除。

3.5 绝不能作为默认补救的行为

不自动降级、不重新上锁、不擦整盘、不重写分区表、不解除 critical 保护、不跨型号刷包、不用论坛里名字相近的镜像覆盖。AOSP 的解锁/锁定机制与 AVB 回滚保护表明，状态转换和版本校验都有独立约束；通用文档不是 Lenovo 特定固件的执行配方。[S07][S08]

“恢复到原厂”也不自动包含“重新上锁”。若将来需要研究 relock，另立任务，重新验证所有分区与验证链；本项目首期不做。

4. 原生 Linux 的两条技术路线

4.1 路线 A：利用匹配的厂商内核，优先获得启动证据

目标是尽量复用已知硬件初始化逻辑，验证自定义启动材料和最小用户空间能否工作。需要匹配版本的内核来源/配置/模块或可合法使用的现有启动材料；不能假定 Lenovo 已发布可复现的完整源码。

拆包时核实启动头版本、压缩格式、ramdisk、设备树、AVB 描述，以及是否有独立 vendor_boot/init_boot。不要从 Android 版本直接推导这些布局。[S10]

优点是可能更快获得日志；主要限制是 Android 显示/GPU/内核接口并不天然变成桌面 Linux 所需的标准接口。“能进 BusyBox”只能证明启动链的一部分。

首个原生实验不接触持久用户数据，不做自动磁盘初始化；默认没有联网服务。启动脚本由另一 Agent 审查所有挂载、格式化、存储探测与启动任务。

4.2 路线 B：主线或接近主线的内核

目标是获得更适合通用 Linux 的驱动接口与维护路径。要逐项确认 SoC、板级设备树、显示面板、触控、存储、无线、电源管理与 GPU。

本次读到了上游 Linux 中的 sm6115.dtsi，只能说明存在可研究的相邻平台代码；不能据此断言与本机完全兼容，更不能直接把它重命名成 TB331FC 设备树。[S18]

选择路线 B 的条件是能够找到具体补丁、维护者、可复现配置或愿意投入板级适配工作；不是因为某个介绍页写着“支持高通”。若没有这些证据，先停止编译大工程，补齐可行性报告。

4.3 图形路径要单独验收

Mesa 的 Freedreno/Turnip 文档提供 Adreno 驱动研究入口；精确支持仍要核对设备表及内核接口。该文档不能证明本机的显示、触摸和 GPU 已能协同工作。[S17]

建议把图形拆成五个检查点：面板点亮、稳定扫描输出、输入设备、可用渲染接口、Wayland 合成器。只看到 /dev/dri 目录或一张亮屏照片，不足以认定 Hyprland 可用。

第一阶段可接受软件渲染用于定位问题，但要在报告中标明 renderer；不得把软件渲染的桌面截图作为硬件加速成功。后续记录 compositor/Mesa/kernel 版本、renderer 字符串、分辨率、输入延迟感受、温度与稳定性。

4.4 电源与键盘不应拖到最后

安全的关机、充电状态、温度监控、正常频率控制和最低限度的输入能力，应早于长时间桌面压力测试。禁止为绕过启动问题而随意取消 thermal、regulator 或充电保护。

键盘若是蓝牙，还要考虑早期启动与加密解锁的输入。Omarchy 的普通安装说明强调早期磁盘解锁需要可用的非蓝牙输入路径；在平板上更不能假定桌面能用的键盘，在 initramfs 中也能用。[S16]

不因为这个问题直接决定取消磁盘加密。先用不含私人数据的最小实验系统验证输入，再设计实际交付形态与数据保护。

5. Omarchy 路线：现在能并行做的事

5.1 Apple Silicon Mac：优先验证官方 Try Omarchy

官方 omacom/try-omarchy 提供 Mac 上的 ARM64 虚拟机体验，适合作为软件兼容性验证环境；它的虚拟 GPU 路径不是平板 Adreno。项目中 USB 直通属于实验功能，首期保持关闭。[S14]

先用 uname -m 确认 Mac 类型。若不是 Apple Silicon，不照搬该安装路径；另选合适的隔离测试环境，记录架构与差异。不要为了这个项目重装 Mac。

虚拟机只共享公开源码、构建产物和已审阅的脱敏报告。不要共享整个 home、SSH 密钥、Android 调试密钥、设备 token 或私人固件目录，也不开放到宿主 ADB 服务的访问。

5.2 ARM 软件包并非自动齐全

Omarchy 软件包仓库已有 aarch64 构建相关代码，但“存在构建支持”不等于“全部依赖都在选定版本的公开仓库中可用”。本次看到的脚本还包含默认架构与按架构选择包的逻辑。[S15]

让 Codex 建立版本矩阵：包名、架构、版本、仓库来源、签名验证方式、依赖、是否实际安装、启动测试结果。先做最小桌面链，再处理可选应用。遇到缺包时不关闭签名检查，不混入不明二进制。

5.3 不运行通用整盘安装器来“试试”

Omarchy 的普通 ISO 安装路径面向磁盘安装，包含清除所选磁盘的流程；它不是 Android 的 boot.img，也不是可直接给 TB331FC 刷入的固件。[S16]

未来在平板上集成时，要先解释每一个系统级配置脚本会改什么。若只移植主题、终端与部分配置，应如实命名为“Omarchy 风格环境”；只有约定的软件集合、会话与更新路径经过验证，才称为本项目的原生 Omarchy 移植。

9. 后续验收：避免把演示当成果

最小启动阶段要有与镜像哈希对应的启动记录，说明日志如何取得、在哪个阶段失败、如何退出；只有 USB 重新枚举不代表内核成功启动。

硬件阶段建议分别验收：显示、触控/外接输入、温度/充电读数、可控关机、存储访问策略、网络、GPU renderer。试验前固定版本和观察时长。可以把“连续运行30分钟、正常关机后重新启动3次”作为初期自定义检查，但它不是稳定性认证。

桌面阶段再验证会话登录、快捷键、屏幕方向、缩放、屏幕键盘、中文输入、网络重连、锁屏解锁以及睡眠恢复。未验证睡眠前，不把合盖/息屏当成安全停机方式。

更新策略必须保留已知可用的内核、固件和恢复材料。桌面包升级与引导组件更新分开控制；不在首个可用版本上自动追最新内核。

10. 后备路线与止损边界

若硬件启动通路暂时未证明，可以保留 Android 做 Termux/Linux 用户空间或远程终端。PRoot 不提供真正的 root、常规 systemd 或内核模块能力；Termux:X11 是 Android 上的图形入口，不能与原生 Linux 混为一谈。[S26][S27]

后备路线只是保留使用价值，不替代用户的原生目标。项目状态应写成“原生路线等待某项证据”，而不是“换个壁纸也算完成”。

本次交付的边界： 已完成公开来源核查、静态代码阅读、策略/任务设计和采集工具的模拟测试；没有访问你的 Mac 或平板，没有登录联想账号，没有申请本机 token，没有下载并验证匹配恢复包，没有证明本机已解锁或 Linux 驱动可用。postmarketOS 部分资料访问受限，保留待核实项。下一步需要实际的、经过脱敏审阅的本机证据。

E. 可选的 bootloader 查询：不是首日默认脚本

只有在 G0 完成、官方资料已核实正确进入/退出方式，并且你明确批准“进入模式做查询”之后，才提出此项。切换模式是额外的状态变化，应单独记录；本包不自动执行。

由 Owner 操作设备进入已确认的 bootloader 模式，核对画面与 USB 设备。不要把 Android 中的序列号自动当作其他模式必定相同的标识。AOSP 区分 bootloader fastboot 与 userspace fastbootd；两者不能混用。[S09]

下面仅是待审核的只读查询集合，变量须由 Owner 根据本次枚举明确设置：

fastboot devices
fastboot -s "$FB_SERIAL" getvar product
fastboot -s "$FB_SERIAL" getvar is-userspace
fastboot -s "$FB_SERIAL" getvar unlocked
fastboot -s "$FB_SERIAL" getvar current-slot

每条单独记录 stdout、stderr、返回码与屏幕状态。Fastboot 常把信息写到 stderr，不能只抓 stdout。变量为空时不得继续。型号无法对应、设备不唯一、超时或返回不支持时停止解释，不补发 OEM 命令，也不改用“全变量+全操作”的自动探测程序。

此集合不含解锁能力的最终证明。不支持 getvar unlocked 也不等于必然锁死。具体 OEM 查询须另给出处与风险解释。

不得为了“确认可用”执行启动镜像、刷写、擦除、格式化、critical unlock、重锁或下载模式转换。

F. 固件离线研究方法

所有固件从明确、可追溯的合法来源取得。建立 templates/firmware-manifest.md，至少写：来源、下载时间、完整文件名、型号/地区/版本证据、SHA-256、包格式、适用工具、签名验证状态和未核实项。

对本地文件可进行摘要与格式识别（路径由你在本地选择）：

shasum -a 256 /path/to/firmware-file
file /path/to/firmware-file

哈希只能识别文件是否相同；没有可信发布哈希/签名时，自己算出的 SHA-256 不能证明文件是官方、匹配或可安全刷入。

离线流程：

  1. 保存不可修改的原始副本，对副本操作；不解压到主目录或脚本目录。先检查归档路径，拒绝路径穿越、符号链接越界与异常解压体积。
  2. 不执行包内脚本、可执行文件或自动刷写配置；在无 USB、无私人目录、无宿主 ADB 通路的沙盒/VM 中分析。
  3. 根据实际格式选工具，固定源码提交和依赖。提取清单、启动头、签名/AVB 元数据、分区映射与设备树信息；缺某项就标未知。
  4. 比对恢复包与本机属性。找不到同版不能自动降级：AVB 等回滚元数据只是分析的一部分，不能代替实际设备策略与早期启动链的版本约束。[S08][S10]
  5. 分开记录 vendor 固件、内核、模块、设备树的来源与版本。相同 SoC、相同 Android 主版本都不是充分匹配条件。

首日不需要完整提取所有分区。优先回答“这包能否作为本机恢复候选”和“能否解释启动结构”，避免花大量时间处理与决策无关的内容。

G. 解锁文件研究方法：先分析，再决定是否提出实验

将研究拆成两个独立对象：生成端与验证端。

生成端：固定仓库提交；逐函数记录输入、格式与长度校验、常量来源、输出布局、网络请求、第三方脚本。使用虚构序列号做纯离线单元测试，不连接设备。不要将生成样本命名成可刷写成品。

验证端：根据匹配固件中的组件与公开源码/符号，识别命令处理和校验路径；无法定位就写明不足。不要因出现某个字符串就推断所有前置条件满足。没有实际解锁结果时，只能得出“验证逻辑假设”。[S04][S05][S06]

若获得你自己的官方解锁文件，在私人环境分析结构元数据；对外只交付必要的脱敏说明。比较文件不意味着重新生成的版本也会被接受。不得把固定签名块误称为获得了厂商签名能力。

H. 最小原生启动实验怎么设计

前提是 G1、G2、G3 均已通过，且另有 G4 操作批准。并不预设某个具体启动命令在 TB331FC 可用。

实验提案必须包含：所用内核/ramdisk/设备树来源、启动头与加载方式证据、镜像哈希、日志出口、对存储的全部潜在访问、供电/温度约束、正常和异常退出方式。

优先只证明：启动到自定义用户空间，并获得可对应镜像的日志。日志可以来自经核实的串口、USB、pstore 或其他路径；不因为“需要日志”就默认要求拆机焊接。若日志依赖重启读取，说明可能覆盖或丢失的窗口。

不运行普通 Linux 发行版的自动磁盘探测/安装向导。不启用不必要的存储写入、扩容、fsck 修复、网络监听或更新任务。即使设计为 RAM 系统，仍须由另一 Agent 审核启动代码；不能称为物理只读保证。

I. 硬件与桌面实验如何形成证据

使用 templates/hardware-report.md 的矩阵，逐项填输入条件、观测、版本、日志文件及可复现步骤。优先电源/温度和输入，再逐步扩展显示、网络、GPU、声音与睡眠。

每次只改变一个可解释的变量，记录前后镜像摘要；失败保留日志，不自动清理现场。热失控迹象、异常充电、无法正常关机、模式退出未验证都触发停止。不要用禁用保护机制换取一张启动截图。

J. 出现意外时的统一流程

停止新命令；保持记录；不要重试写入。Owner 根据预先批准的退出方式处理设备，Agent 只整理最后一次操作、镜像哈希、供电和枚举状态。

禁止 Agent 因为“已经坏了”自动获得更高权限。新的恢复步骤是新的操作提案，必须重新核对固件、设备模式、目标与风险。未经验证的低级模式不主动上传程序。
