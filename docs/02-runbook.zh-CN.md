# 方法手册：从本机证据到下一项实验

适用基线：TB331FC / 照片版本 ZUX OS 1.1.10.680。研究日期 2026-09-30。  
先读 `01-strategy.zh-CN.md`；本手册不包含可直接执行的解锁/刷写序列。

## A. 主机准备

确认环境（可由 Agent 执行）：

```bash
uname -m
sw_vers
python3 --version
git --version
claude --version
codex --version
```

`arm64` 与 `x86_64` 决定后续虚拟机选择，不根据“Mac”二字猜测。记录实际工具版本；缺哪个工具，就先报告缺失，不自动安装一大套环境。

采集工具需要 Python 3.9+ 和 Android Platform Tools。Homebrew 当前官方条目给出的安装命令如下；**仅由你在同意安装时执行**，不是采集脚本自动动作。[S20][S21]

```bash
brew install --cask android-platform-tools
adb version
fastboot --version
```

也可以从 Google 官方页面取得 macOS Platform Tools，审阅后配置 PATH。不要下载论坛打包的“ADB 一键工具”。不要为了本项目修改全局 shell、全局 Agent 权限或自动接受所有 sudo 操作。

## B. 固定采集工具：默认不碰设备

在项目根目录执行：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
python3 scripts/collect_readonly.py
```

第二条只输出查询计划，不查询设备、不启动 ADB。工具采用标准库、固定查询集合、显式目标、超时停止，不提供任意 shell 命令入口。

代码审阅重点：`QUERIES`、`query_argv`、`collect_device`、`execute`。测试验证程序逻辑，**不证明 macOS USB、ADB 版本或平板固件的行为**。

## C. 由 Owner 执行一次真实采集

先手动备份重要资料，确认设备正常。开发者选项中启用 USB 调试属于你执行的配置动作；不要顺手打开 OEM 解锁。随后确认只有一个 Agent 在操作设备，没有后台自动任务。

连接**唯一的一台**平板，授权你自己的 Mac。不要连接其他 Android 设备或启动 Android 模拟器。你在独立本地终端运行：

```bash
adb devices -l
python3 scripts/collect_readonly.py --collect
```

脚本会要求你输入本机 USB 序列号，输入默认不回显。将上一条输出中的序列号只在本地输入，不粘贴到 Agent 聊天。默认保存位置：

```text
~/.local/share/tb331fc-owner-only/<时间-随机后缀>/
  inventory.private.json
  inventory.redacted.json
```

也支持 `--serial`，但参数会进入命令行/可能的 shell 历史，因此不作为推荐的人工作法。没有交互终端且未指定序列号时，脚本停止。

脚本要求 ADB 枚举中有 USB 标志、设备状态正常、只有一个设备且型号严格匹配 TB331FC；不满足就停止。不同 ADB 实现若不显示 USB 标志，**不要删掉校验直接重跑**，先让双方分析原因和更可靠的替代验证。

采集后查看返回码及 `status`；`collection_completed` 只代表采集流程完成，不代表字段全部可读，更不代表可以解锁。

### 采集覆盖与明确不覆盖

| 覆盖 | 不覆盖 |
|---|---|
| 精确型号、系统/硬件属性、内核、部分布局信息、电池状态 | 用户数据备份、原始分区备份 |
| 固定列表中的锁状态提示字段 | 对 BL 可解锁性的保证 |
| 本地 ADB 路径、版本、哈希与命令返回 | 官方工具签名真实性的自动认证 |
| 查询失败、空值与中断 | root、权限升级、自动重连/重试 |
| 过滤版与私人版报告 | 所有个人信息必定被过滤的保证 |

没有读取完整 getprop、完整 logcat、应用列表、联系人、Wi-Fi 配置或设备解锁 token。部分固定输出仍可能含标识或构建信息，所以过滤版也须人工检查。

“只读”指不请求分区/设置/固件写入；ADB 授权与正常 Android 运行可能产生日志和状态变化。这不是取证级零写入工具。

## D. 脱敏和证据交接

过滤版最初仍保存在私有目录。你检查后，只把必要内容复制到 `artifacts/approved-input/`，例如 `inventory-owner-reviewed.json`。默认目录是空的，Agent 不得自己去私人目录寻找报告。

不要把真实 SN、Bootloader_SN、解锁文件、完整固件、私钥或官方账户页面交给公共仓库。Bootloader_SN 若确需用于官方流程，可由 Agent 按官网说明读取后显示给你填写，不写入任何文件；该属性不在本包自动采集列表中。[S01]

Agent 用 `templates/hardware-report.md` 解释每一条值。`unknown_empty`、`unknown_error` 都应保留为未知；不把 `0`、空字符串、不支持命令三者混在一起。对照设备照片与 Android 属性，发现矛盾先停止推断。

## E. 可选的 bootloader 查询：不是首日默认脚本

只有在 G0 完成、官方资料已核实正确进入/退出方式，并且你明确批准“进入模式做查询”之后，才提出此项。**切换模式是额外的状态变化，应单独记录；本包不自动执行。**

由 Owner 操作设备进入已确认的 bootloader 模式，核对画面与 USB 设备。不要把 Android 中的序列号自动当作其他模式必定相同的标识。AOSP 区分 bootloader fastboot 与 userspace fastbootd；两者不能混用。[S09]

下面仅是待审核的只读查询集合，变量须由 Owner 根据本次枚举明确设置：

```bash
fastboot devices
fastboot -s "$FB_SERIAL" getvar product
fastboot -s "$FB_SERIAL" getvar is-userspace
fastboot -s "$FB_SERIAL" getvar unlocked
fastboot -s "$FB_SERIAL" getvar current-slot
```

每条单独记录 stdout、stderr、返回码与屏幕状态。Fastboot 常把信息写到 stderr，不能只抓 stdout。变量为空时不得继续。型号无法对应、设备不唯一、超时或返回不支持时停止解释，不补发 OEM 命令，也不改用“全变量+全操作”的自动探测程序。

此集合不含解锁能力的最终证明。不支持 `getvar unlocked` 也不等于必然锁死。具体 OEM 查询须另给出处与风险解释。

**不得为了“确认可用”执行启动镜像、刷写、擦除、格式化、critical unlock、重锁或下载模式转换。**

## F. 固件离线研究方法

所有固件从明确、可追溯的合法来源取得。建立 `templates/firmware-manifest.md`，至少写：来源、下载时间、完整文件名、型号/地区/版本证据、SHA-256、包格式、适用工具、签名验证状态和未核实项。

对本地文件可进行摘要与格式识别（路径由你在本地选择）：

```bash
shasum -a 256 /path/to/firmware-file
file /path/to/firmware-file
```

哈希只能识别文件是否相同；没有可信发布哈希/签名时，自己算出的 SHA-256 **不能证明文件是官方、匹配或可安全刷入**。

离线流程：

1. 保存不可修改的原始副本，对副本操作；不解压到主目录或脚本目录。先检查归档路径，拒绝路径穿越、符号链接越界与异常解压体积。
2. 不执行包内脚本、可执行文件或自动刷写配置；在无 USB、无私人目录、无宿主 ADB 通路的沙盒/VM 中分析。
3. 根据实际格式选工具，固定源码提交和依赖。提取清单、启动头、签名/AVB 元数据、分区映射与设备树信息；缺某项就标未知。
4. 比对恢复包与本机属性。找不到同版不能自动降级：AVB 等回滚元数据只是分析的一部分，不能代替实际设备策略与早期启动链的版本约束。[S08][S10]
5. 分开记录 vendor 固件、内核、模块、设备树的来源与版本。相同 SoC、相同 Android 主版本都不是充分匹配条件。

首日不需要完整提取所有分区。优先回答“这包能否作为本机恢复候选”和“能否解释启动结构”，避免花大量时间处理与决策无关的内容。

## G. 解锁文件研究方法：先分析，再决定是否提出实验

将研究拆成两个独立对象：**生成端**与**验证端**。

生成端：固定仓库提交；逐函数记录输入、格式与长度校验、常量来源、输出布局、网络请求、第三方脚本。使用虚构序列号做纯离线单元测试，不连接设备。不要将生成样本命名成可刷写成品。

验证端：根据匹配固件中的组件与公开源码/符号，识别命令处理和校验路径；无法定位就写明不足。不要因出现某个字符串就推断所有前置条件满足。没有实际解锁结果时，只能得出“验证逻辑假设”。[S04][S05][S06]

若获得你自己的官方解锁文件，在私人环境分析结构元数据；对外只交付必要的脱敏说明。比较文件不意味着重新生成的版本也会被接受。不得把固定签名块误称为获得了厂商签名能力。

## H. 最小原生启动实验怎么设计

前提是 G1、G2、G3 均已通过，且另有 G4 操作批准。并不预设某个具体启动命令在 TB331FC 可用。

实验提案必须包含：所用内核/ramdisk/设备树来源、启动头与加载方式证据、镜像哈希、日志出口、对存储的全部潜在访问、供电/温度约束、正常和异常退出方式。

优先只证明：启动到自定义用户空间，并获得可对应镜像的日志。日志可以来自经核实的串口、USB、pstore 或其他路径；不因为“需要日志”就默认要求拆机焊接。若日志依赖重启读取，说明可能覆盖或丢失的窗口。

不运行普通 Linux 发行版的自动磁盘探测/安装向导。不启用不必要的存储写入、扩容、fsck 修复、网络监听或更新任务。即使设计为 RAM 系统，仍须由另一 Agent 审核启动代码；不能称为物理只读保证。

## I. 硬件与桌面实验如何形成证据

使用 `templates/hardware-report.md` 的矩阵，逐项填输入条件、观测、版本、日志文件及可复现步骤。优先电源/温度和输入，再逐步扩展显示、网络、GPU、声音与睡眠。

每次只改变一个可解释的变量，记录前后镜像摘要；失败保留日志，不自动清理现场。热失控迹象、异常充电、无法正常关机、模式退出未验证都触发停止。不要用禁用保护机制换取一张启动截图。

## J. 出现意外时的统一流程

停止新命令；保持记录；不要重试写入。Owner 根据预先批准的退出方式处理设备，Agent 只整理最后一次操作、镜像哈希、供电和枚举状态。

禁止 Agent 因为“已经坏了”自动获得更高权限。新的恢复步骤是新的操作提案，必须重新核对固件、设备模式、目标与风险。未经验证的低级模式不主动上传程序。
